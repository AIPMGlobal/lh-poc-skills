# LH PoC 발표

기술을 만든 과정을 넘어 **어떤 업무가 달라졌고, 조직에 왜 중요하며, 어디까지 활용할 수 있는지** 설명한다. 이야기의 흐름은 신한DS 과정에서 다듬은 경영진 보고 방식을 그대로 쓰고, 양식과 색과 글쓰기만 LH에 맞춘다. 과제마다 실제 근거에 맞는 가치와 전개를 고른다. 모든 과제에 같은 효과 문구를 붙이지 않는다.

교육생 대부분은 개발자가 아니다. 대화에서는 어려운 용어를 풀어서 말한다.

## 설득 장치 다섯 가지를 먼저 점검한다

정확하지만 조심스럽기만 한 발표는 기억에 남지 않는다. [우수 발표의 설득 장치](references/persuasion-devices.md)를 읽고, 자료에서 아래 항목을 먼저 찾는다.

1. **문제의 숫자:** 업무 빈도, 걸리는 사람 시간, 관여하는 인원.
2. **한 줄 전후 대비:** 같은 구간, 같은 단위의 전후 한 쌍. 예: `회차당 4시간 → 30분`.
3. **실제 화면:** 실제 출력이나 실행 화면 한 장과 사용 순서.
4. **사람과 AI의 역할:** 최종 책임자와, 코드와 AI와 사람이 각자 하는 일을 한 문장으로.
5. **LH 방향과 현재 위치:** 공식 방향 한두 개, 지금 단계와 다음 단계.

자료에 있는 것은 구성에 넣고, 없는 것은 교육생에게서 끌어낸다. 숫자는 `실측 → 경험 추정 → 구간 선택 → 미측정` 순서로 묻는다. 교육생이 답한 값은 '담당자 경험 추정'으로 쓴다. 세 단계를 모두 물어도 없으면 그 숫자는 쓰지 않는다. 스킬이 숫자를 지어내거나 '가정'으로 채우지 않는다.

## 화면에는 성과를 싣고, 남은 것은 말로 한다

발표는 과제를 설득하는 자리다. 슬라이드 화면에는 **확인한 결과와 가치만** 싣는다.

- 화면에 쓰지 않는 것: 놓친 사례, 실패 건수, '보완 중', '확인 필요', '미측정', '검증 미완료', "~가 아닙니다" 식의 문장.
- 그 내용이 가는 곳: 발표자 노트의 `구두 보충` 단락(질문이 나오면 답할 내용)과 질문 대비용 숨김 부록 한 장.
- 수치의 성격(실측, 담당자 경험 추정, 목표)은 본문 큰 숫자 옆이 아니라 하단 출처 줄에 한 번 적는다.
- 포장과 거짓은 다르다. 하지 않은 것을 했다고 쓰지 않는다. 숫자를 만들지 않는다. 가상 데이터 시험 단계를 현업 운영 중이라고 쓰지 않는다. 현재 위치는 표지와 단계 장에 사실대로 표시한다.
- 시험에 쓴 자료의 종류와 범위(가상 데이터, 건수, 기준일)는 한계가 아니라 결과의 조건이다. 표지의 현재 위치, 결과 장의 부제, 하단 출처 줄 중 맞는 곳에 긍정문으로 적는다. 예: `가상 데이터 500건 시험`.
- 교육생이 한계를 화면에 넣어 달라고 하면 그 요청을 따른다.

## 먼저 논의하고, 합의한 흐름으로 제작한다

기본 흐름은 **자료 읽기 → 발표 이야기 제안 → 교육생과 수정과 논의 → 최종 PPT 제작**이다. [대화와 구성 제안](references/dialogue-workflow.md)을 먼저 읽는다.

- 처음에는 과제의 의미를 한두 문장으로 제안하고, `장 / 이야기할 내용 / 들어갈 근거` 세 열의 표로 발표 흐름을 보여 준다. 열두 장 구성이 출발점이며 자료에 맞게 합치거나 뺀다.
- 구성표 아래에 설득 장치 다섯 가지의 상태를 한 줄씩 적는다(있음 / 끌어낼 것 / 없음).
- 그 아래에 `화면에는 넣지 않고 말로 할 것`을 두세 줄로 적는다.
- 구성을 제시한 뒤 이야기의 방향을 바꿀 질문 1~3개만 묻는다. 빠진 숫자와 실제 화면 요청을 우선한다.
- "이 방향 좋아"는 논의를 이어 가자는 뜻이다. "이 구성으로 PPT 만들어 줘"처럼 제작 요청이 오면 합의한 흐름으로 파일을 만든다. 사용자가 논의를 건너뛰고 바로 만들라고 하면 그 요청을 따른다.
- 제작 단계에서 목차를 새로 만들지 않는다. 마지막으로 합의한 핵심 메시지, 장 순서, 주장, 근거를 쓴다.

## 1. 자료에서 주장과 근거를 분리한다

PRD, Agent 정의서, As-Is/To-Be 자료, 데모 웹 페이지, 화면 캡처, 결과 Excel, 보고서 초안, 멘토링 메모를 있는 만큼 읽는다. 같은 자료의 버전이 여럿이면 가장 최신 것을 쓰고 어느 버전인지 알린다.

[근거와 규모 판단](references/evidence-and-scale.md)을 읽는다. 내부 작업용으로 `주장 / 출처와 위치 / 대상, 기간, 단위 / 확인 상태 / 발표 표현`을 기록한다. 주요 주장은 다음 연결 중 어디까지 확인됐는지 판단한다.

> 수행한 작업 → 실제 산출물 → 사람이 활용한 방식 → 확인된 조직 효과

구현, 시험, 현업 운영, 다른 조직으로의 확산은 다른 상태다. 가상 데이터 시험만으로 현업 성과를 추정하지 않는다.

## 2. 이번 과제의 의미를 선택한다

[가치 경로 선택](references/value-paths.md)을 읽는다. 기술 이름보다 업무 문제에서 출발해 근거가 가장 강한 가치 하나를 중심으로 잡는다.

> 어떤 업무 문제였는가 → 무엇을 바꿨는가 → 담당자의 일이 어떻게 달라지는가 → 무엇을 확인했는가 → 조직에 어떤 의미인가

**TR²Q는 이야기 안에 녹인다.** 업무 소개에는 반복 빈도와 적용 범위(R), 기존 문제에는 실패 영향(Risk), 업무 흐름에는 사람 시간과 검토 부담(T), 실제 결과물에는 정확성과 사용 가능성(Q)을 연결한다. 자료와 관련 없는 축은 억지로 채우지 않는다. 별도 TR²Q 표는 사용자가 요청하거나 실제 비교에 유용할 때만 쓴다. R은 업무 반복 빈도이며 줄이는 목표나 리스크의 약자가 아니다.

사업 규모는 맥락이지 성과액이 아니다. 관련 없는 시장 규모나 가상의 비용 절감, ROI를 넣지 않는다.

## 3. 외부 동향, LH 방향, 확장을 과제에 연결한다

도움이 될 때 [외부 동향과 전략 연결](references/external-trends.md)을 읽는다. 외부 사례는 방향의 근거이지 우리 구현 수준의 증거가 아니다. LH 방향은 공식 원문을 확인한 뒤 `공식 방향 → 이번 업무의 변화 → 기여 방식`으로 연결한다. 다른 업무로의 확장은 재사용할 부분과 새로 정할 부분을 구분해 말한다.

## 4. 듣는 사람의 질문에 답하는 흐름을 만든다

[보고 구성과 장표 작성](references/story-patterns.md)과 [기준 전개](references/base-flow.md)를 읽는다. 목차부터 채우지 말고 각 장에 `판단 질문 / 답 / 새 근거 / 제목`을 적는다.

표지 다음 장은 핵심 요약이다. 한 줄 전후 대비, 확인한 결과, 운영 방식, 오늘의 요청(없으면 다음 단계)을 한 장에 담는다. 실제 결과물은 앞쪽에서 주요 증거로 쓴다. 평가 방식과 통과율은 결과의 신뢰성을 설명하는 근거이지 발표의 중심이 아니다. 마지막 장은 요약을 되풀이하지 않고 과제의 의미를 한 문장으로 닫는다.

## 5. 업무 흐름과 역할은 도식으로 그린다

전후 업무 흐름, 코드와 AI와 사람의 역할, 사람이 확인하는 지점, 적용 단계는 글보다 그림이 빠르다. [도식 그리기](references/diagrams.md)를 읽고 자료의 관계에 맞는 도식을 고른다. 업무 순서, 구성과 범위, 현행과 개선의 항목 대비, 확인한 항목, 걸러지는 과정은 AntV Infographic 템플릿으로 먼저 그린다. [Infographic 템플릿으로 도식 그리기](references/infographic.md)에서 검증한 템플릿과 문법을 따른다. 반려 경로가 있는 역할 레인, 단계별 시간이 붙은 현행과 개선, 현재 위치 표시는 `kit` 도우미로 그린다.

어느 쪽이든 도식은 편집 가능한 도형과 선으로 들어간다. Infographic 결과도 그림으로 붙이지 않고 `kit.infographic`이 도형과 글상자로 바꿔 넣는다. 발표 직전에 팀이 직접 고칠 수 있어야 하기 때문이다. 구현하지 않은 연결을 실제 흐름처럼 그리지 않는다.

## 6. LH 양식으로 파일을 만들고 확인한다

[장표의 증거 배치](references/executive-slide-design.md), [LH 발표 디자인](references/design-system.md), [제작과 검증](references/production.md)을 따른다. 색은 LH 슬로건과 권장양식 보고서에서 가져온 값이고, 표지는 LH 권장양식의 구성을 따른다. 글꼴은 LH 업무용 PC에 모두 있는 맑은 고딕이다. 본문은 LH 개조식(□, ㅇ, -, *)으로 쓰고 가운뎃점은 쓰지 않는다.

하단 왼쪽에는 출처 줄, 오른쪽에는 발표 부서 이름과 쪽 번호를 둔다. 발표자 노트에는 장마다 발표 대본을 먼저 쓰고 그 아래 `구두 보충` 단락을 둔다. 숨김 부록은 마지막 장에 표 한 장으로 만든다.

전체 슬라이드를 화면으로 바꿔 제목의 논리, 글자 넘침, 도식의 선과 겹침, 출처와 수치 조건을 확인한다. `python scripts/audit_pptx.py <결과.pptx>`로 구조를 보조 검사한다. 파일을 만들지 못했으면 완성됐다고 말하지 않는다.

## 전달 전 확인

- 교육생과 논의한 흐름, 핵심 메시지, 양식을 최종 파일에 유지했는가?
- 설득 장치 다섯 가지 중 자료가 허용하는 것을 모두 썼는가? 빠진 것은 교육생에게 알렸는가?
- 화면에 놓친 사례, 보완 예정, 확인 필요, 미측정 같은 문구가 남지 않았는가? 그 내용이 구두 보충과 숨김 부록에 들어갔는가?
- 하지 않은 것을 했다고 쓴 곳, 스킬이 만든 숫자가 없는가? 수치의 성격이 하단 출처 줄에 한 번 있는가?
- 가상 데이터라는 조건과 건수가 표지, 결과 장, 출처 줄 중 한 곳에 있는가? 화면에 개인정보가 남지 않았는가?
- 실제 산출물과 업무 변화가 보이는가? 시험 과정 설명이 주인공이 되지 않았는가?
- 시간, 빈도, 실패 영향, 품질을 이야기 안에서 자연스럽게 설명했는가?
- 도식이 실제 업무 순서와 맞는가? 사람이 확인하는 지점이 보이는가?
- Infographic 도식의 글자가 16px 이상인가(`warning` 없음)? 검증한 템플릿 표 밖의 템플릿을 썼다면 화면으로 확인했는가?
- LH 로고와 슬로건의 비율과 색을 바꾸지 않았는가?
